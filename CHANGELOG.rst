Change log
##########

This document records changes to pioweave in the style of Amaranth's ``changes.rst``: one section per version, with the entries grouped under Added, Changed and Removed. Dates are ISO 8601. Facts about hardware are marked ``[verify]`` where they are not checked; nothing has run on a chip.

Version 0.1.0 (unreleased)
===================
Added
-----

- ``pioweave.builder``: a Python builder for PIO programs with one method per instruction (``Program``), the operand constants, directives (``.side_set``, ``.wrap``, ``.fifo``, ``.mov_status``, ``.in``, ``.out``, ``.set``, ``.clock_divider``), labels, an encoder written from the RP2040 and RP2350 datasheets (equal to ``pioasm`` on 10,681 words in 351 programs), ``pio_text()``, ``words()``, ``write_pio()`` and ``PioError``. It needs no Amaranth.
- The Amaranth front end (``pioweave``): ``PioDesign``, the platforms ``RP2040PioPlatform``, ``RP2350PioPlatform``, ``RP2350APioPlatform``, ``RP2350BPioPlatform``, ``RP2354PioPlatform``, ``RP2354APioPlatform`` and ``RP2354BPioPlatform``; the FSM-to-PIO compiler (``compile_design``, ``PioCompileError``) that refuses anything that would change the cycle behaviour; the data path (``platform.shifter`` with ``pull``, ``push``, ``out``, ``in_``); ten example designs.
- ``pioweave.emulator``: a cycle-by-cycle emulator of the PIO blocks (four state machines, shared instruction memory, FIFOs, IRQ flags, pins, PIO versions 0 and 1) with ``PioBlock``, ``run_case``, ``run_compiled``, ``to_vcd`` and ``EmulationError``. It needs no Amaranth.
- ``pioweave.boards``: board definitions with named pins for the Raspberry Pi Pico, the Pico 2, the WeAct Studio RP2350B core and the Waveshare Core2350B.
- Project writers: ``platform.build()`` writes a ``.pio`` file, a ``bitweave.toml`` case with the expected waveforms taken from the Amaranth simulation, a README, and on request a Pico SDK C project or a MicroPython program (``SimOptions``, ``write_project``, ``PioProjectError``).
- The command line ``python -m pioweave``: ``list``, ``build`` (the generator command for bitweave), ``emulate`` (run a design in the emulator and print the pin waveforms, optionally a VCD), ``doctor`` (check the environment), ``new`` (scaffold a project from a template, ``new --list`` shows the templates) and ``--version``.
- Several state machines in one design (``pioweave.block``, docs/blocks.rst): ``Block``, ``Machine``, ``BlockSim`` and ``platform.block()`` run single-machine designs as state machines 0 to 3 of one PIO block with shared IRQ flags (``IrqHub``, ``IrqPort``: a flag set and cleared in the same cycle ends up set) and shared pins (the highest-numbered machine wins a GPIO several write, a machine reads what another drives with one cycle of delay). ``Block.compile`` places the programs one after the other from address 0 (at most 32 instructions in all, one GPIO window for the block); ``block_run`` simulates the block in Amaranth, ``emulate_block`` runs the compiled programs together in the emulator, and ``Block.build`` writes one ``.pio`` file with a program per machine, a ``bitweave.toml`` with one case per machine (each replays the environment of the machine, ``machine_cases``) and, for ``pico-c``, a ``main.c`` that claims the state machines, loads the programs at their offsets and starts them with ``pio_enable_sm_mask_in_sync``. Four example blocks (``uart_baud``, ``handshake``, ``ring``, ``shared_pin``; ``python -m pioweave list / build / emulate`` accept them), ``examples/block`` and ``tests/example_blocks.json``. Refused with a reason: more than four machines, more than 32 instructions in all, machines that need different GPIO windows, ``irq ... rel``, a GPIO written by two machines with an instruction that can stall, the MicroPython project. Pin directions work inside a block: the directions are per GPIO (the initial direction is the OR of the machines' initial directions, ``set`` / ``out`` / ``mov pindirs`` and a side-set that writes directions change it for all machines), the pad of an input GPIO is the stimulus, the one-machine cases carry ``expect_dirs`` (``solo_expectations``), and ``main.c`` sets the direction of every driven GPIO once more at the end. Nothing has run on a chip.
- ``examples/``: runnable examples (blink on a board LED, a UART transmitter and receiver, a WS2812-style waveform, a square wave generator, a unittest of a program in the emulator), run by ``tests/test_examples.py`` and described in ``docs/examples.rst``.
- The version gate: ``import pioweave`` accepts Amaranth 0.5.0 to 0.5.10 and one tested 0.6 development commit (``UnsupportedAmaranth``, ``PIOWEAVE_ALLOW_UNTESTED=1``), and ``scripts/matrix.sh`` runs the suite against other versions.
- Error messages of the builder, the compiler, the project writer and the version gate carry a short ``hint:`` line with what to change for the most common mistakes; the original text is unchanged.
- ``python -m pioweave.emulator.check PROGRAM_JSON CASE_JSON`` (``pioweave.emulator.check.check_case`` and ``main``): runs one bitweave simulation case, given as the JSON ``pioasm -o json`` writes and the case as a JSON object, in the emulator and prints one JSON object (``ok``, ``error``, the pad and direction waveforms, the words received, the FIFO counts, the final registers, the keys it does not support), so that bitweave's ``cross_check = "pioweave"`` can compare the two simulators; tested directly and against bitweave's ``pio`` flow on random programs.
- Pin directions in the Amaranth front end: ``platform.directions(buffer, init)`` gives a pin group a direction register; ``sh.out(m, d, n)`` is ``out pindirs``, ``sh.mov(m, d, src)`` is ``mov pindirs`` (PIO version 1), ``d.eq(C)`` alone in a state is ``set pindirs`` and in a state with other work it is a side-set that writes directions (``.side_set N opt pindirs``). The simulations report the pad (the design's output where the pin is an output, the stimulus elsewhere) and the directions per cycle (``amaranth_run(...)["dirs"]``, ``expect_dirs`` in the generated case), the C project sets the initial directions per run of equal bits, and two example designs (``open_drain``, ``bus_turnaround``) show the forms.
- Input checks and limits (security audit): project and program names are plain identifiers (``pioweave._validate``) at every entry point, also under ``python -O``; simulation options, waveforms, words and clocks are validated; ``--cycles`` is limited to 1,000,000 (``--max-cycles`` lifts it); user errors on the command line are ``error: ...`` with status 2; ``emulator.check`` exits 0 or 2 on any input and reads at most 16 MiB (``--max-bytes``); pathological designs raise ``PioCompileError``; the builder refuses the clock dividers, non-ASCII names and unhashable operands that pioasm refuses; the emulator checks pin numbers, counts, words and offsets at the call; a pioasm that cannot run or hangs gives ``PioProjectError``; a project is not written through a symbolic link.
- The version gate runs when ``pioweave`` is imported (from the package metadata of the installed Amaranth, without importing it) and again when the compiler is imported; the override issues ``UntestedAmaranthWarning``; ``scripts/matrix.sh`` prints one result line per version and exits non-zero when any version fails or is refused.
- Packaging: the classifier ``Private :: Do Not Upload``, ``PDM_BUILD_SCM_VERSION`` or the placeholder ``0.0.0.dev0+nogit`` for a build without git, ``pdm-backend<3``, no private pdm-backend import; the CI workflow reads only, pins its actions by commit and runs Python 3.14 too.
- Documentation in reStructuredText (Sphinx, with the examples run by ``sphinx-build -b doctest``): getting started, designing for PIO, the data path, the builder, the emulator, boards, projects, compatibility, testing, examples, releasing, the API reference and the design notes.
